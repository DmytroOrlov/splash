# Tasks: Battery-Aware Suspension and Recovery

**Input**: Current design artifacts in `specs/001-battery-aware-suspension/` and `.specify/memory/constitution.md`.

**Prerequisites**: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/control-readiness-and-lifecycle-status.md`, and `quickstart.md`.

**Organization**: Dependency-ordered implementation boundaries. Story labels trace tasks to the specification; the architecture proof gates deliberately precede tasks that depend on them.

**Task format**: Every task has a checklist ID. `[P]` appears only where file/ownership boundaries and dependencies allow independent work. Each task identifies its production/test files, dependency, focused evidence, mechanical gate, and STOP condition. Gate tasks are verification checkpoints over seams that earlier implementation tasks already establish; a checkpoint may add only a narrow missing proof test, and a failed checkpoint stops and returns evidence instead of performing a broad corrective refactor.

## Acceleration / senior-finish contract

The implementation may use early **manual vertical-slice milestones** to get a runnable system sooner, but those milestones are validation aids only. They do not replace, weaken, or mark complete any remaining task or gate.

- **Slice S1 — after T023**: exercise one live native generation through manual `ready -> battery intent -> draining -> actual Engine/RuntimeModel/ModelPackage release -> suspended`, while status/control remain usable and no second `ReadyEvent` is emitted. Power-source automation is deliberately not required for this milestone.
- **Slice S2 — after T026**: exercise manual `ready -> suspended -> recovery -> ready` in the same process generation, including compatible warm restore and safe cold fallback. Python effective-context consumption and real power-source automation may still be pending.
- T027–T032 remain required for the final feature even if S1/S2 work interactively. A successful demo is not feature acceptance.

Known review/proof obligations are assigned rather than discarded:

1. **T023** must isolate the dual suspension barrier: prove model/request drain may already be satisfied while retained `Cache::transfersInFlight()` is still true, and that residency is not destroyed until the transfer barrier also clears.
2. **T024** must harden `FileRestore` before transactional recovery depends on it: successful `finish()` is commit-once, and `cancel()` prevents any later commit even when IO had already completed. This is API hardening for recovery, not a T022 requirement.
3. **T025** must exercise an actual failing `FileRestore` through the Engine/recovery-candidate path and prove no destination lane/candidate promotion survives, while the immutable retained source remains retryable.
4. **T030** must close the remaining real-stack preservation proof gap with a deterministic Qwen + `Cache` + `SlotFile` asynchronous offload failure (or an equivalently strong production-path fault seam), proving no false reusable warm publication. Do not add a production debug API solely for fault injection.
5. **T032 final acceptance** must confirm these assigned obligations were closed by their owner tasks or superseded by stronger concrete evidence; none may silently disappear because an earlier manual slice worked.
6. **T025/S2 warm latency** must prove that compatible recovery reuses the retained matching prefix on the first real request rather than replaying the full agent-session prefill; model/runtime load and model-only kernel preparation are reported separately.

## Execution strategy and stop policy

1. Execute Phases 1–2 first; Gate A is the first architectural stop point and must include the RuntimeBootstrap construction/ownership evidence from T005.
2. Establish detached model-less control/readiness semantics, the model-less Frontend/HTTP construction seam, and Gate F foundation before lifecycle automation.
3. Prove native admission/drain and asynchronous IO quiescence before any destructive release path.
4. Prove warm preservation (Gate B) and payload safety (Gate C) before consuming or claiming retention of warm state; Gate B failing globally blocks the feature, while an individual preservation miss falls cold and Gate D remains sufficient to prove safe release so recovery falls cold without preventing suspended publication.
5. Implement ordered suspend release, then transactional candidate (Gate E), then publish effective context natively and consume it in Python through the existing status path.
6. Finish battery startup, repeated toggles, intent races, and Gate F end-to-end focused evidence.

Every code-changing task ends with its named focused target(s) and `git diff --check`; broader repository tests are not routine task gates. Tests use explicit barriers/tickets/events for race proofs, never elapsed-time sleeps. Gate tasks are checkpoints over earlier implementation tasks: a failed gate stops and returns exact evidence rather than performing a broad corrective refactor. A task that uncovers an architectural contradiction stops at that task and reports the artifact/ownership evidence. Do not implement a workaround, broaden scope, or mutate the protected design artifacts from this decomposition.
